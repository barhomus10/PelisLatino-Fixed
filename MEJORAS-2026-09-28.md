# PelisLatino HD — revisión y mejoras del StreamResolver (2026-09-28)

El resolver de vsembed **ya funcionaba** para películas. Esta revisión lo dejó funcionando
también para **series**, evitó un error que rompía la compilación y corrigió tres fallos
que hacían que algunas películas/episodios cayeran al reproductor WebView.

---

## 1. Error crítico: `app/src/main/java/dza/folbol/BLABONGO/StreamResolver.java` NO COMPILABA

Un parche anterior insertó el bloque "VSEMBED FIX" entre la declaración
`public static class StreamResult` y su cuerpo, dejando la clase sin abrir y con el cuerpo
huérfano 300 líneas más abajo:

```
 93:  public static class StreamResult      <- sin "{"
 94:  // === VSEMBED FIX ===                <- métodos del resolver metidos dentro
395:  {                                     <- cuerpo huérfano
```

**Resultado:** `JavaSyntaxError` → el módulo no compilaba.
**Arreglado:** cuerpo de `StreamResult` reubicado junto a su declaración y llave sobrante eliminada.
Verificado: los **47 archivos `.java` del repo parsean sin errores**.

---

## 2. Las SERIES no funcionaban (fallo silencioso)

La URL real de un episodio que entrega playpaste es:

```
https://vsembed.ru/embed/tv?imdb=tt5615700&season=1&episode=1&ds_lang=es
```

El código solo detectaba `"/tv/"` o `"type=tv"` → **los episodios se pedían como `type=movie`**.
Además, el `window.CONFIG` del reproductor de TV **no trae el campo `"api"`**: trae
`"streamBase"` (sin season/episode), así que el resolver lanzaba `CONFIG.api no encontrado`.

**Arreglado en `PelisStreamResolver.resolveVsEmbed()` y `StreamResolver.resolveVsEmbedFast()`:**

1. Detección de TV: `/tv/`, `type=tv`, `/embed/tv` **o** `season`+`episode` en la query.
2. `vs_src.php?type=tv&id=...&season=S&episode=E`.
3. API: usa `CONFIG.api` si existe; si no, compone
   `streamBase + &season=S&episode=E + &stream_urls`.

## 3. `generate.php` devuelve 429 y el token se desperdiciaba

Medido en vivo:

| llamada | respuesta |
|---|---|
| 1.ª | token JWT de 211 B → **válido** |
| 2.ª y 3.ª | HTML `429 Too Many Requests` de 569 B → el master responde `invalid token` |

El token es un JWT con `exp - iat = 14400 s` (4 h) ligado a `ip_cidr`, así que **no hace falta
pedirlo cada vez**.

**Arreglado:** caché de token por host (`TOKEN_CACHE` / `TOKEN_EXP`) respetando el claim `exp`,
backoff de 2 s y un reintento cuando llega un 429, y bucle de reintentos (3 intentos × espejos)
que refresca el token solo si el master llega con `invalid token` / `no token` / 403.

---

## 4. Se elegía el servidor equivocado

`PelisDetailActivity.elegirServidor()` mostraba el diálogo siempre que había más de un servidor.
`vimeus.com` (opción `alt`) responde **Cloudflare 522** desde hace días, mientras que vsembed
(`ds_lang=es`) es el único verificado.

**Arreglado:** si hay opción en español (vsembed / `ds_lang=es`) se usa directamente, sin preguntar.
Si no existe, se mantiene el diálogo de siempre.

## 5. El reproductor no usaba el resolver bueno

`PlayerActivity.resolverStreamEnSegundoPlano()` llamaba siempre al `StreamResolver` genérico
(solo WebView), que con vsembed se queda en timeout y terminaba en el reproductor WebView
aunque sí había stream.

**Arreglado:** nuevo `resolverInteligente(url)` → si la URL es vsembed / `ds_lang=es` /
cloudorchestranova usa `PelisStreamResolver` (WASM + Token) y solo si falla cae al genérico.

## Cómo instalar

Los `.java` de la raíz son las fuentes reales de la app (paquete `dza.folbol.BLABONGO`).
Copia los que corresponda a `app/src/main/java/dza/folbol/BLABONGO/` de tu proyecto
(sobreescribiendo). No dejes los `.java` sueltos dentro del `sourceSet` de Gradle:
`StreamResolver.java` existe tanto en la raíz como en `app/src/main/java/...` y Android
Studio daría "duplicate class" si los compila los dos.
